# AI_Advent_Challenge_#9_Day6

AI-агент с тремя стратегиями управления контекстом и памятью диалога.

## Стратегии контекста

| Стратегия | Принцип | Затраты |
|---|---|---|
| **Sliding Window** | Хранит только последние N сообщений, остальное отбрасывает | Без доп. вызовов |
| **Sticky Facts** | Извлекает факты в ключ=значение, отправляет факты + окно | +1 вызов LLM на обновление фактов |
| **Branching** | Создаёт checkpoint и ветки диалога, переключается между ними | Без доп. вызовов |
| Сжатие с резюме | Rolling-резюме старой истории | +1 вызов LLM на обновление резюме |
| Полная история | Отправляет всё | Без доп. вызовов |

Sliding, Facts и Branching — основные стратегии этого дня (без summary).

## Сравнение на сценарии «Сбор ТЗ» (10 сообщений, yandex/gpt-5-lite)

| Стратегия | Поведение | Финальный ответ |
|---|---|---|
| **Sliding (окно 4)** | Забывает первые 6 сообщений | «Уточните, о каком проекте» — потеря контекста |
| **Sticky Facts** | Помнит все 10 сообщений через факты | Описывает 4-5 ключевых требований |
| **Branching (ветки А и Б)** | Две независимые траектории от чекпоинта | Ветка А: «бюджетные решения»; Ветка Б: «премиум-решения + обратная связь» |

**Выводы:**
- Sliding Window экономит токены, но теряет контекст на длинных диалогах
- Sticky Facts сохраняет ключевые данные даже на сотнях сообщений через сжатие в факты
- Branching позволяет исследовать альтернативные пути развития диалога без потери истории

**Примечание к Sticky Facts:** для корректного извлечения фактов требуется модель, уверенно работающая с JSON (deepseek-v4-pro, openai/gpt-4.1, anthropic/claude-opus-5). На слабых моделях (yandex/gpt-5-lite) извлечение фактов может давать пустой ответ.

## Модель памяти агента

Три слоя памяти с явным разделением данных:

| Слой | Хранит | Жизненный цикл | Управление |
|---|---|---|---|
| **Краткосрочная** | Текущий диалог — последние N сообщений | Очищается вместе с чатом | Автоматически |
| **Рабочая** | Данные текущей задачи: цели, ограничения, спецификации, статус | Живёт до явной очистки | Агент предлагает → пользователь подтверждает ИЛИ ручное добавление |
| **Долговременная** | Профиль, предпочтения, принятые решения, накопленные знания | Переживает сессии | Агент предлагает → пользователь подтверждает ИЛИ ручное добавление |

### Как работает

1. После каждого ответа агент вызывает модель повторно (temperature=0) с промптом `MEMORY_SUGGEST_PROMPT` — просит проанализировать диалог и предложить, что сохранить в рабочую и долговременную память.
2. Предложения отображаются в модальном окне «Память» (кнопка в шапке) с кнопками **Принять все** / **Отклонить**.
3. Пользователь может вручную добавлять, редактировать и удалять записи в рабочей и долговременной памяти.
4. Все три слоя включаются в system prompt отдельными секциями: `## Память агента → ### Рабочая память / ### Долговременная память`.

### Проверка

| Вопрос | Без памяти | С памятью |
|---|---|---|
| «Как меня зовут?» | «Вы не представились» | «Иван» (из долговременной памяти) |
| «Какой бюджет?» | «Не знаю» | «7 млн рублей» (из рабочей памяти) |

Разные типы памяти сохраняются отдельно: рабочая в `memory.working`, долговременная в `memory.long_term`, краткосрочная — это `history`.

- **Выбор модели:** из `ai-public` и `nvidia` NIM
- **Промпт (роль):** Ассистент, Пошагово, Аналитик, Инженер, Критик
- **Стратегия контекста:** выбор из 5 режимов
- **Параметры:** температура, Top_P, Frequency/Presence penalties
- **Лимиты:** токенов ответа, слов, размера вопроса

## Сохранение истории

История, факты и ветки сохраняются в `app/data/chat_history.json` с атомарной записью. При перезапуске сервера полное состояние восстанавливается.

## MCP: инструменты и планировщик (Day 17–18)

Галочка **«Подключить MCP-сервер (GitHub)»** в настройках (⚙) даёт агенту инструменты MCP-сервера `app/mcp_server.py`. Сервер работает **постоянно** (streamable HTTP, `http://127.0.0.1:5183/mcp`). Внутри него фоновый поток-планировщик раз в 5 секунд выполняет задачи, у которых подошло время. Данные хранятся в SQLite: `app/data/scheduler.db`.

| Инструмент | Что делает |
|---|---|
| `github_repo_info`, `github_recent_commits` | данные репозитория прямо сейчас |
| `schedule_repo_watch(owner, repo, interval_minutes≥5)` | **периодический сбор данных**: звёзды, форки, issues, новые коммиты → таблица `snapshots` |
| `schedule_reminder(text, in_minutes)` | **отложенное** напоминание → лента |
| `schedule_summary(interval_minutes≥1)` | **регулярная сводка**: агрегирует замеры за период и публикует в ленту |
| `get_summary(hours)` | агрегированный результат за N часов (Δ звёзд/форков/issues, число коммитов, напоминания) |
| `publish_summary_now()` | сводка с момента предыдущей → в ленту |
| `list_scheduled_jobs`, `cancel_scheduled_job` | управление задачами |
| `get_feed(after_id)` | лента: сводки, напоминания, ошибки |

Кнопка **📰 Сводки** в шапке открывает список задач (с отменой), кнопку «Сводка сейчас» и ленту. Интерфейс опрашивает ленту раз в 15 секунд: новые сводки и напоминания всплывают уведомлением, а на кнопке появляется счётчик непрочитанных.

Пример диалога (галочка MCP включена, модель с поддержкой tool calling):
- «Следи за pallets/flask и fastapi/fastapi каждые 10 минут»
- «Делай сводку каждые 30 минут»
- «Напомни через 5 минут проверить сводку»
- «Что изменилось за последние 2 часа?» → `get_summary(hours=2)`

Веб-сервер поднимает MCP-сервер сам. Чтобы планировщик работал 24/7 независимо от веб-интерфейса, запустите его отдельно: `run_mcp.bat`. Лимит GitHub без токена — 60 запросов в час, поэтому интервал наблюдения не меньше 5 минут. Переменная `GITHUB_TOKEN` поднимает лимит до 5000 в час.

## Композиция MCP-инструментов: пайплайн (Day 19)

Три инструмента в том же MCP-сервере образуют цепочку:

```
search_github_repos ──search_id──► summarize_search ──summary_id──► save_to_file ──► app/data/exports/*.md|json
   (получает данные)                 (обрабатывает)                   (сохраняет)
```

| Шаг | Инструмент | Вход | Выход |
|---|---|---|---|
| 1. search | `search_github_repos(query_text, limit, sort)` | поисковый запрос GitHub | `search_id` + краткий список |
| 2. summarize | `summarize_search(search_id)` | ID результата шага 1 | `summary_id`, статистика (звёзды, языки, лицензии, темы, лидеры) и обзор в Markdown |
| 3. saveToFile | `save_to_file(summary_id, filename, format)` | ID результата шага 2 | имя файла, размер, SHA-256 |

Каждый шаг сохраняет результат в таблицу `artifacts` (SQLite) и передаёт дальше **только ID**. Поэтому данные между шагами не искажаются, даже если цепочку ведёт LLM. Если передать ID артефакта не того типа, шаг вернёт понятную ошибку.

`run_pipeline(query_text, limit, sort, filename, format)` выполняет всю цепочку **автоматически** одним вызовом и возвращает:
- трассу шагов: вход и выход каждого, время;
- проверки передачи данных: summarize получил `search_id` шага 1, совпали число и список репозиториев, save получил `summary_id` шага 2, SHA-256 файла сверен, содержимое файла равно результату шага 2.

**Как запустить:**
- **Кнопкой 🔗 Пайплайн в шапке:** форма запуска, цепочка шагов карточками, отметки проверок, превью обзора и список сохранённых файлов со ссылками на скачивание.
- **Из чата** (галочка MCP): «найди топ-10 MCP-серверов на Python, обобщи и сохрани в файл mcp_python». Агент вызовет `run_pipeline` или три шага по очереди, передавая ID.

## Архитектура

- `app/agent.py` — логика агента, три стратегии, извлечение фактов
- `app/llm.py` — клиент к API (ai-public + nvidia), поддерживает tool calling
- `app/store.py` — сохранение/загрузка состояния в JSON
- `app/server.py` — HTTP-сервер (+ `/api/mcp/tools`, `/api/scheduler/*`)
- `app/mcp_server.py` — MCP-сервер: GitHub API + планировщик + SQLite
- `app/mcp_bridge.py` — клиент MCP: запуск сервера, tool-calling цикл LLM ↔ MCP
- `web/` — фронтенд без сборки
